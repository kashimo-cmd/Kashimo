# K09 Controller

- Out: `pi/controller/main.py`, `ws_server.py`, `telemetry.py`, `events.py`, `tests/test_controller.py`.
- Did: `Controller` wires K04-K08. States MANUAL, STOPPED, LINK_LOST. `step()` every 50 ms (sensors, drive, head, rod, path, events, TELEMETRY every second tick = 10 Hz). `imu_step()` every 10 ms (IMU, yaw, calibration end, BUMP, ALERT_TILT, watchdog). `read_slow()` every 2 s in a thread (Wi-Fi, CPU, recording flag). Wiring follows `docs/tasks/K08.md` and the rules of K05-K07: `set_direction` through Drive, `head.step` before `rod.step`, `rod.state` and `imu.status` passed to `Drive.step`, `drive.moving` passed to `rod.request`.
- Watchdog: armed by the first valid CONTROL (a bad message does not count). 500 ms without one: `drive.stop()` (latch, enable low), state LINK_LOST, EVENT LINK_LOST. First CONTROL after that: EVENT LINK_BACK, latch stays, START is refused until the heartbeat is back. It is checked every 10 ms, so the motors go off 0.50 to 0.51 s after the last CONTROL. Measured on a PC with mock HW, 5 runs: 0.504 to 0.506 s.
- Events: SQLite `robot.db` (`--db`, env `KASHIMO_DB`, git-ignored). Ids only grow, also across restarts. SYNC replays ids above `since_id`. If the disk write fails the event is kept in RAM and still broadcast. Deleting `robot.db` restarts ids at 1: reload the dashboard, it ignores ids it has already seen.
- Server (aiohttp, port `ws_port`): `/ws`, static `/alerts/` (dir `runs/alerts`, env `KASHIMO_ALERTS_DIR`), internal endpoints answer 127.0.0.1 and ::1 only (403 otherwise). A client that cannot take a message in 250 ms is closed so it reconnects and sends SYNC.
- Internal contract for K11 (4.5 leaves the bodies open): `GET /internal/state` returns `{pan, tilt, led, rod, moving, head_moving, s, slab}`. `POST /internal/event` takes `{"data": {score, frame, heat, detector}}` (kind is ALERT_DEFECT, the only one allowed); the controller adds the current pose. `POST /internal/ai_status` takes `{ai, ai_ms}`; no post for 5 s [EST] shows `OFF`. The AI worker writes frames and heat maps into the alerts dir.
- Mock mode: `HW_MODE=mock python -m pi.controller.main` simulates the robot (encoders and gyro follow the applied PWM, track gauge 0.2 m) so `tools/ws_smoke.py` has motion to show. `--no-sim` turns it off. Run: `python -m pi.controller.main --port 8765`, then `python tools/ws_smoke.py`.
- Telemetry: no Wi-Fi reading shows -100 dBm, junk numbers become 0 (never an exception). `rec` is true when `/run/kashimo/frames/latest.jpg` (env `KASHIMO_FRAMES`) was written in the last 5 s: a proxy for the video pipeline, not a read of MediaMTX.
- Slabs: `floor((x - origin_m) / slab_width_m) + 1` from `slabs.json`; a missing file falls back to `gallery.slab_width_m`. `overrides` is read as `{"<computed number>": number}` (the spec leaves its format open).
- A loop error cuts the motors through `hw.safe_stop()` and latches; the loop keeps running.
- Tests: 34 in `tests/test_controller.py` (mock HW with a fake clock, plus a real asyncio server with a websockets client, plus a real `python -m pi.controller.main` process driven by `tools/ws_smoke.py`). The WebSocket and HTTP tests need `aiohttp` and `websockets` (skipped if missing). 30 deliberate code breaks were all caught. Run on a PC only. NOT RUN on the Pi.
- Found by CI: `tools/ws_smoke.py` (K03) starved its own heartbeat on a slow runner; fixed there (deadline-based send), 6 of 6 runs pass under heavy CPU load.
- Not done (CHECK ON PI): real I2C, GPIO and `iw`; the 100 Hz IMU loop under real load; `FRAMES` path; sonar thread timing with the 50 ms loop; keeping the 50 ms loop steady with the AI worker running. No `/video.mjpg` (the config still names it, K10 does not provide it).
